# Stage 1 — Fit check (1.1) and full evaluation (1.2–1.4)

Part of the [agent guide](../AGENTS.md). **Load when:** a job description arrives, or the user asks for an evaluation, comparison or storyboard. **Also read:** [the shared evaluation standard](evaluation.md), [plain language](writing/plain-language.md) for the tables and prose you write.

A supplied job description starts an evaluation of the entire available career record, not resume generation. Use current career records and relevant original CV sections; later user-confirmed corrections take precedence over legacy claims. The schema explains records but is not evidence. Do not infer experience from titles, keywords or adjacent work. Distinguish explicit requirements, preferred qualifications and responsibilities.

Stage 1 has two parts.

- **1.1 Fit check** is the default response to a job description: the verdict and the questions that could change it. Stop after it for the user's go/no-go decision.
- **1.2–1.4 Full evaluation** adds the asks-and-stories table, storyboard and review before build. Produce it when the user asks to continue, or with 1.1 in one pass when they ask for the full Stage 1 at the start. Continue in the same session where possible; a new session must reread the evidence.
- Stage 2 may follow 1.1 directly. Stage 2 then works through 1.2–1.4 privately before drafting and records the result compactly in `plan.md` ([hidden, not skipped](stage-2-resume.md#hidden-not-skipped)). The user sees only the 1.1 output and can ask for the full 1.2–1.4 at any time.

**Each fact has one home:** evidence and scores live only in the table; the other sections point to it with placeholders instead of restating it. Keep to the stated limits; they cut repetition, never qualifiers.

### Preparation (always)

1. **Job-description key.** Quote every bullet of the responsibilities, requirements and nice-to-have sections **verbatim**, and give each a section tag (Do-1, Want-1, Nice-1) by [Classifying asks](evaluation.md#classifying-asks): the tag sets the weight. From the rest of the posting, tag only what a candidate can be measured against: **conditions** as one tag each for location, onsite or remote schedule, travel and work authorization, wherever the posting states them (`Cond-1`, `Cond-2`, …), each with a shorthand (for example `= Columbus, OH`) because the card shows it; a location in the posting's header gets its own condition tag and is never skipped; a condition the posting never mentions gets no tag and does not appear on the card; **context a candidate must fit** (what the company sells, to whom, in which domain or stage) as at most three `About` tags; and role-description sentences as `Role` tags only when they state an ask no Do, Want or Nice bullet already covers. Give each piece of text one tag; `render` rejects overlapping spans, so split a bullet whose parenthesis states a separate preference. Skip the job title, the reporting line (unless it changes the job, for example no other team members in the same role), company claims, culture slogans, market size, funding, offices, benefits and legal text, each with a short `skip` reason. Do not paraphrase, trim or merge quoted text. Where you can run Python, build the key with `tools/jd_key.py` (standard library only; run it with no arguments for usage). `number` prints the posting with line numbers. Then, in one command, write a map that tags each line or sentence (splitting paragraphs that hold several asks) and give each tag a **shorthand** after `=`; `render <jd> - --save tags.json > key.md <<'MAP'` … `MAP` copies the exact text into the key. Never retype the key. It fails on phrases that do not match verbatim, duplicate tags, untagged substantive text and shorthands that add or change words; fix the map and rerun. Deciding what each passage asks remains your judgment; agents that cannot run code type the key by hand.
   - **Source guard:** where you can run Python, ingest the posting first and render through the guard; when an ingested artifact exists, this step is required. Use `python3 job-search/tools/jd_ingest.py ingest` with `--source-type user_paste` for a posting the user pastes, or `--source-type hiringcafe` and its provenance for one from a search. Then `lines DIR` shows each line's block, and `render DIR - --save tags.json > key.md <<'MAP'` replaces `jd_key.py render`; write the map exactly as for jd_key. The guard checks the source hash and quotes before jd_key runs. It rejects a tag that takes only some lines of a wrapped block: to split a paragraph or bullet into several asks, quote each part with a span and tag every part. A posting marked `truncated` is incomplete: say so, and ask for the full posting before scoring what is missing. If the adapter cannot run, use `jd_key.py` as above and do not describe the key as source-verified. See [JD ingestion](../job-search/jd-ingestion.md).
   - **Shorthand rule:** trim the quote to its ask. Keep the employer's action verb and what it acts on, and any qualifier that sets the bar (for example "without relying on authority", "not just validate decisions", "direct-to-consumer commerce"). In requirement tags (Do, Want, Nice, Role), never drop words that set the level of the requirement, such as "extensive", "complex", "high-impact", "proven", "exceptional", "independently" or any number; `render` rejects a shorthand that drops one. Drop other intensifiers, examples and decoration. Keep a list that defines what qualifies (the domains, systems or tools that count, often after a colon); drop a list that only illustrates. Use only the quote's own words, in order; you may add "and", "or" and commas. If a trim does not read smoothly, keep a longer unbroken phrase from the quote instead of adding words. Example: "you want to understand the loops, behaviors and incentives that create lasting business impact" → want to understand behaviors and incentives that create impact. Apply [plain language](writing/plain-language.md) when choosing what to keep.
   - **Placeholders:** use `{Do-1'}` for job wording outside the key. The key holds the full quotes. Run `jd_key.py assemble tags.json <files> > stage1.md` to expand shorthands and group adjacent tags. The script quotes exact excerpts, italicizes trims and rejects unknown tags, missing shorthands and full-quote placeholders.
2. **Shared evaluation.** Read [the shared standard](evaluation.md) for the rubric, grouping, weights, conditions and bounded adjustment. Rate every tag in a private `scores.txt`: 0–4 with the record IDs behind any score above 0 (score 0 when the records hold nothing on the point; where you can run Python, first try `python3 tools/current_view.py --search` with the posting's words and likely alternatives), or pass, fail or unknown for Cond tags, set by [the shared conditions](evaluation.md#conditions): run `python3 tools/conditions.py --location "…" --workplace …` for location, workplace and travel where you can run Python, and judge the rest against [career goals and preferences](../career/preferences.md). Mark each ask that names a personal disposition by adding `trait` after its score. Use `groups.json` to map repeated tags to one competency; every measured non-condition tag belongs to exactly one group when groups are supplied. Never merge away source wording or let a broad ask hide independent AND requirements. Run `jd_key.py assemble --scores scores.txt --groups groups.json --assessment-out assessment.json` with the report files (add `--stale` when the posting is older than the search criteria's `stale_after_days`, three weeks by default). It requires every tag, rejects unknown record IDs, prints a summary for you only, lists requirements scored 1 or below, and computes the final fit, label and requirements met with the `shared-2` engine. Omit groups only when the tags already represent unique competencies. A nonzero adjustment needs `--adjustment` and `--adjustment-reason`; otherwise leave it at zero. Use the assessment's final fit and label in the verdict. Conditions stay outside the math: any failed condition means Deprioritize, and an unknown that could change the decision becomes a question. Update the underlying rating first when new information changes it. The 1.1 verdict lines name only the strongest drivers, not every score. In 1.2–1.4, show each requirement scored 1 or below in its own table row or under **Not covered**; never hide one in a merged row. Scores never appear in the report or in chat.

### 1.1 Fit check: the verdict card

Chat shows the card: items 1–4 below. The delivered file holds the card plus item 5. Keep the card short enough to read at a glance; the detail lives in 1.2–1.4.

1. **Heading:** `### Company · Role`, followed on the next line by the pay range when the posting states it, and then a **Conditions** line showing every condition tag as ✓ pass, ✗ fail or ? unknown, for example `**Conditions:** ✓ New York · ✓ hybrid, 50% in office · ? travel not stated`. An unknown that could change the go decision also becomes one of the questions.
2. **Verdict** (three lines). Line 1: `**Fit: NN%**` (the engine's final fit, 0–100%), followed by baseline and adjustment, a ten-block bar (one ▰ per 10%, rounded; ▱ for the rest), **requirements met** (for example `7 of 9 requirements met`), then the label `assemble` computed under [the shared label rule](evaluation.md#one-calculation-one-adjustment-policy-and-one-label), in bold and never chosen by hand: **Promising**; **Stretch: [what moved it or the named question that could lift it]**, naming the critical gap, the required ask scored 2 or the 1.1 question; or **Deprioritize**, naming the failed condition or the low fit. The user may still choose to pursue any of them. Line 2: `- **Strengths:**` with at most three placeholders for the asks that carry the score. Line 3: `- **Gaps:**` with at most three placeholders for the asks that limit it. Every résumé is tailored, so do not recommend tailoring. This is editorial judgment, not an ATS score or hiring probability; secondary matches must not obscure critical gaps. When the report is built with `assemble`, deliver it as a file: `fit-check.md` in the application's output folder (for example `output/<company-role>/`), which Stage 2 later saves in the build snapshot. In chat, show the card (items 1–4), copying the heading, conditions line, three verdict lines and questions unchanged from the assembled file (`assemble` expands the placeholders; the Fit line is yours); never restate the verdict in your own words. The job-description key stays in the file.
3. **Review before build** (optional, one line): include it only when a presentation risk could change the user's go decision, for example a functional title the employer is likely to check. Otherwise it waits for 1.4.
4. **Questions:** at most four, only those that could materially change a score or the story selection. Each names what it could move, for example "could strengthen {Want-9'} from related work to the same work"; name evidence strength in words, never as a score. Firsthand clarification may suffice; do not require documents unnecessarily.
5. **Job-description key and Not mapped**, as `render` printed them, for reference. File only; never paste the key into chat.

Keep the map, `tags.json`, `scores.txt`, any `groups.json` and `assessment.json` for 1.2–1.4. In 1.1, `assemble` lists most tags as unused because the table does not exist yet; act on that list only in 1.2.

### 1.2–1.4 Full evaluation

Read the [full evaluation module](stage-1-full-evaluation.md) when the user asks for the full evaluation, and before Stage 2 plans a résumé. The fit check does not need it.

**Selections from search:** work from the exported `application_queue.json` or the saved run folder, which hold the postings and search evaluations. Given only a choices file, follow [Acting on a choices file](job-search.md#selection-and-handoff): find the run or ask, never rank a subset, and say how many picks were evaluated.

**Multiple job descriptions:** say in the first line that a ranked comparison comes first and that the full Stage 1 for each follows on request (offer it for all of them in one reply). Evaluate them in two passes.
1. **Comparison first.** Evaluate each description against the whole record under the same evidence standards, but show only a ranked comparison table: **Rank | Role | Fit % | Label | Strongest fit | Must-have gaps (score 0–1) | Tradeoffs**. Do not build asks-and-stories tables or storyboards yet. Do not average away a critical gap or assume the highest score is the user's preferred role. Stop for the user to choose which roles to pursue.
2. **Fit check and full evaluation for the chosen roles only.** Build 1.1 and, on request, 1.2–1.4 for each selected role. A role's fit estimate may change once its full table is built; if it does, state the change and the reason.

Carry each selected role's Stage 1 output (1.1 and any of 1.2–1.4) into Stage 2.

**Stop after 1.1, or after 1.2–1.4 when requested, for the user's go/no-go decision.** A job description alone does not authorize Stage 2. If the user explicitly authorizes both stages, proceed without asking again.

In an application session, capture new information for the [handoff](handoff.md). In an information update session, apply the [information update procedure](information-update.md). Keep job-specific evaluations outside permanent career facts.
