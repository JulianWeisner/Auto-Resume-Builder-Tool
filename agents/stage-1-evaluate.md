# Stage 1 — Fit check (1.1) and full evaluation (1.2–1.4)

Part of the [agent guide](../AGENTS.md). **Load when:** a job description arrives, or the user asks for an evaluation, comparison or storyboard. **Also read:** [plain language](writing/plain-language.md) for the tables and prose you write.

A supplied job description starts an evaluation of the entire available career record, not resume generation. Use current career records and relevant original CV sections; later user-confirmed corrections take precedence over legacy claims. The schema explains records but is not evidence. Do not infer experience from titles, keywords or adjacent work. Distinguish explicit requirements, preferred qualifications and responsibilities.

Stage 1 has two parts.

- **1.1 Fit check** is the default response to a job description: the verdict and the questions that could change it. Stop after it for the user's go/no-go decision.
- **1.2–1.4 Full evaluation** adds the asks-and-stories table, storyboard and review before build. Produce it when the user asks to continue, or with 1.1 in one pass when they ask for the full Stage 1 at the start. Continue in the same session where possible; a new session must reread the evidence.
- Stage 2 may follow 1.1 directly. Stage 2 then works through 1.2–1.4 privately before drafting and records the result compactly in `plan.md` ([hidden, not skipped](stage-2-resume.md#hidden-not-skipped)). The user sees only the 1.1 output and can ask for the full 1.2–1.4 at any time.

**Each fact has one home:** evidence and scores live only in the table; the other sections point to it with placeholders instead of restating it. Keep to the stated limits; they cut repetition, never qualifiers.

### Preparation (always)

1. **Job-description key.** Quote every bullet of the responsibilities, requirements and nice-to-have sections **verbatim**, and give each a section tag (Do-1, Want-1, Nice-1). From the rest of the posting, tag only what a candidate can be measured against: **conditions** as one tag each for location, onsite or remote schedule, travel and work authorization, wherever the posting states them (`Cond-1`, `Cond-2`, …); a location in the posting's header gets its own condition tag and is never skipped; **context a candidate must fit** (what the company sells, to whom, in which domain or stage) as at most three `About` tags; and role-description sentences as `Role` tags only when they state an ask no Do, Want or Nice bullet already covers. Give each piece of text one tag; `render` rejects overlapping spans, so split a bullet whose parenthesis states a separate preference. Skip the job title, the reporting line (unless it changes the job, for example no other team members in the same role), company claims, culture slogans, market size, funding, offices, benefits and legal text, each with a short `skip` reason. Do not paraphrase, trim or merge quoted text. Where you can run Python, build the key with `tools/jd_key.py` (standard library only; run it with no arguments for usage). `number` prints the posting with line numbers. Then, in one command, write a map that tags each line or sentence (splitting paragraphs that hold several asks) and give each tag a **shorthand** after `=`; `render <jd> - --save tags.json > key.md <<'MAP'` … `MAP` copies the exact text into the key. Never retype the key. It fails on phrases that do not match verbatim, duplicate tags, untagged substantive text and shorthands that add or change words; fix the map and rerun. Deciding what each passage asks remains your judgment; agents that cannot run code type the key by hand.
   - **Shorthand rule:** trim the quote to its ask. Keep the employer's action verb and what it acts on, and any qualifier that sets the bar (for example "without relying on authority", "not just validate decisions", "direct-to-consumer commerce"). In requirement tags (Do, Want, Nice, Role), never drop words that set the level of the requirement, such as "extensive", "complex", "high-impact", "proven", "exceptional", "independently" or any number; `render` rejects a shorthand that drops one. Drop other intensifiers, examples and decoration. Keep a list that defines what qualifies (the domains, systems or tools that count, often after a colon); drop a list that only illustrates. Use only the quote's own words, in order; you may add "and", "or" and commas. If a trim does not read smoothly, keep a longer unbroken phrase from the quote instead of adding words. Example: "you want to understand the loops, behaviors and incentives that create lasting business impact" → want to understand behaviors and incentives that create impact. Apply [plain language](writing/plain-language.md) when choosing what to keep.
   - **Placeholders:** use `{Do-1'}` for job wording outside the key. The key holds the full quotes. Run `jd_key.py assemble tags.json <files> > stage1.md` to expand shorthands and group adjacent tags. The script quotes exact excerpts, italicizes trims and rejects unknown tags, missing shorthands and full-quote placeholders.
2. **Private scores.** After reading the evidence, score every tag in the key 0–4 with this score key (4 🟢 same work, with a clear result · 3 🟢 same work, but in a different setting, or the result is unclear or recalled · 2 🟡 related work that shows the skill indirectly · 1 🟠 thin, adjacent or unconfirmed evidence · 0 🔴 nothing in the records), including About and Role tags; condition tags are marked pass, fail or unknown instead (see below). Score 0 when the records hold nothing on the point (where you can run Python, first try `python3 tools/current_view.py --search` with the posting's words and likely alternatives), and keep 1 for thin, adjacent or unconfirmed evidence; a gap in the record is a reason to ask, not to raise the score. Conditions are a pass/fail filter, not part of the fit: check each condition tag against [career goals and preferences](../career/preferences.md) and mark it `pass` (it matches), `fail` (it conflicts) or `unknown` (the posting or the records leave it open) in scores.txt, for example `Cond-1 pass`. They never enter the fit estimate. Record the scores in a private `scores.txt` (one `TAG SCORE` per line). Pass it to `assemble --scores scores.txt`, which requires every tag, prints a summary for you only and lists requirements scored 1 or below. **Fit estimate:** mark each ask that names a personal trait (for example high standards, attention to detail, drive or adaptability) by adding `trait` after its score; the career record shows traits only indirectly. `assemble` prints the **fit baseline**: the weighted average of the scores ÷ 4 × 100, with condition tags left out, About and trait tags at half weight and all other tags at full weight. The final fit is the baseline adjusted by at most 5 points as your judgment, with a one-sentence reason in the run log; no adjustment is fine. A domain or industry the posting requires as a qualification is a Want tag at full weight, not an About tag. The 1.1 verdict lines name only the strongest drivers, not every score. In 1.2–1.4, show each requirement scored 1 or below in its own table row or under **Not covered**; never hide one in a merged row. Scores never appear in the report or in chat.

### 1.1 Fit check: the verdict card

Chat shows the card: items 1–4 below. The delivered file holds the card plus item 5. Keep the card short enough to read at a glance; the detail lives in 1.2–1.4.

1. **Heading:** `### Company · Role`, followed on the next line by the pay range when the posting states it, and then a **Conditions** line showing every condition tag as ✓ pass, ✗ fail or ? unknown, for example `**Conditions:** ✓ New York · ✓ hybrid, 50% in office · ? travel not stated`. An unknown that could change the go decision also becomes one of the questions.
2. **Verdict** (three lines). Line 1: `**Fit: NN%**` (documented fit, 0–100%), a ten-block bar (one ▰ per 10%, rounded; ▱ for the rest), then the recommendation in bold, set by the fit band: **80% or more: Pursue**; **70–79%: Pursue, and address [named gap]** (in the résumé summary, cover letter or interview preparation); **60–69%: Stretch: pursue only if [named question] is answered yes**, naming the 1.1 question that could lift the fit; **below 60%: Deprioritize**. Whatever the fit, recommend **Deprioritize** when any condition fails, and name it. The user may still choose to pursue. Line 2: `- **Strengths:**` with at most three placeholders for the asks that carry the score. Line 3: `- **Gaps:**` with at most three placeholders for the asks that limit it. Every résumé is tailored, so do not recommend tailoring. This is editorial judgment, not an ATS score or hiring probability; secondary matches must not obscure critical gaps. When the report is built with `assemble`, deliver it as a file. In chat, show the card (items 1–4), copying the heading, conditions line, three verdict lines and questions unchanged from the assembled file (`assemble` expands the placeholders; the Fit line is yours); never restate the verdict in your own words. The job-description key stays in the file.
3. **Review before build** (optional, one line): include it only when a presentation risk could change the user's go decision, for example a functional title the employer is likely to check. Otherwise it waits for 1.4.
4. **Questions:** at most four, only those that could materially change a score or the story selection. Each names what it could move, for example "could lift {Want-9'} from 2 to 3". Firsthand clarification may suffice; do not require documents unnecessarily.
5. **Job-description key and Not mapped**, as `render` printed them, for reference. File only; never paste the key into chat.

Keep the map, `tags.json` and `scores.txt` for 1.2–1.4. In 1.1, `assemble` lists most tags as unused because the table does not exist yet; act on that list only in 1.2.

### 1.2–1.4 Full evaluation

Read the [full evaluation module](stage-1-full-evaluation.md) when the user asks for the full evaluation, and before Stage 2 plans a résumé. The fit check does not need it.

**Multiple job descriptions:** Evaluate them in two passes.
1. **Comparison first.** Evaluate each description against the whole record under the same evidence standards, but show only a ranked comparison table: **Rank | Role | Fit % | Recommendation | Strongest fit | Must-have gaps (score 0–1) | Tradeoffs**. Do not build asks-and-stories tables or storyboards yet. Do not average away a critical gap or assume the highest score is the user's preferred role. Stop for the user to choose which roles to pursue.
2. **Fit check and full evaluation for the chosen roles only.** Build 1.1 and, on request, 1.2–1.4 for each selected role. A role's fit estimate may change once its full table is built; if it does, state the change and the reason.

Carry each selected role's Stage 1 output (1.1 and any of 1.2–1.4) into Stage 2.

**Stop after 1.1, or after 1.2–1.4 when requested, for the user's go/no-go decision.** A job description alone does not authorize Stage 2. If the user explicitly authorizes both stages, proceed without asking again.

In an application session, capture new information for the [handoff](handoff.md). In an information update session, apply the [information update procedure](information-update.md). Keep job-specific evaluations outside permanent career facts.
